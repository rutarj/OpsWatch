# OWASP Top 10 for LLM Applications (2025): how OpsWatch addresses each

| # | Risk | In OpsWatch | Where |
|---|---|---|---|
| LLM01 | Prompt injection | Ticket text is wrapped in `<ticket>` tags and labeled untrusted in the prompt and in every MCP response. A regex scanner flags injection attempts; flagged tickets force every proposal to high risk and human review. Structurally, even a successful injection can only create a proposal, because the agent has no approve tool. | `guardrails/injection.py`, `triage/llm.py`, `app.py::safe_ticket_view`, `mcp_server.py` |
| LLM02 | Sensitive information disclosure | Emails, phone numbers, Canadian SINs and Luhn-valid card numbers are redacted before text reaches the LLM or the agent. Only counts of redactions are logged, never values. | `guardrails/pii.py` |
| LLM03 | Supply chain | Dependencies are declared with version floors in `pyproject.toml`. The ML model file is created by this project only (joblib can execute code on load, so third-party model files are never loaded). | `triage/ml.py` |
| LLM04 | Data and model poisoning | Training data is generated deterministically and checked into the pipeline; the eval gate in CI catches accuracy drops a poisoned change would cause. | `seed.py`, `config/eval_gate.toml` |
| LLM05 | Improper output handling | Claude answers only through a forced tool call with enum-constrained fields; output is re-validated in code; invalid output falls back to rules. Every proposal payload is schema-validated before storage. The console renders all text with `textContent` (no HTML injection). | `triage/llm.py::_parse`, `actions.py::_validate_payload`, `web/console.html` |
| LLM06 | Excessive agency | The core design: read tools are read-only, write tools only propose, no approve tool exists, separation of duties, high-risk actions need senior approvers, P1 and security resolutions are blocked for agents, change freezes are enforced. | `mcp_server.py`, `guardrails/policy.py`, `actions.py` |
| LLM07 | System prompt leakage | The system prompt contains no secrets, only the taxonomy and rules. Attempts to extract it are flagged by the injection scanner (`system_prompt_probe`). | `triage/llm.py`, `guardrails/injection.py` |
| LLM08 | Vector and embedding weaknesses | KB search uses TF-IDF over a curated, internal article set, so there's no user-writable embedding store to poison. If embeddings are added, KB writes must go through the same approval flow. | `kb.py` |
| LLM09 | Misinformation | Every triage has a confidence score; low confidence, P1 and security tickets always go to human review; the eval measures accuracy and publishes failure cases, including confidently wrong ones. | `triage/service.py`, `reports/EVALUATION.md` |
| LLM10 | Unbounded consumption | Per-agent hourly proposal limit, per-ticket open-proposal cap, `max_tokens=400` per LLM call, the hybrid triager only sends uncertain tickets to Claude, and the eval caps LLM calls (`--llm-limit`). | `config/policy.toml`, `triage/llm.py` |
